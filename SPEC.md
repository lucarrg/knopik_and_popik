# 1. Цель и границы проекта

«Кнопик & Попик» — личный кулинарный сайт для хранения, просмотра и совместного ведения рецептов пользователем и Кириллом. Сайт должен выглядеть как полноценный публичный веб-сайт, а не как локальная заметка или учебный прототип, при этом редактирование контента доступно только двум владельцам.

## Ключевые цели

- Хранить рецепты в структурированном виде с фотографиями, категориями, ингредиентами, шагами, заметками, рейтингом и статусом проверки.

- Позволять быстро находить рецепты через каталог, поиск, фильтры и сортировку.

- Помогать выбрать блюдо через отдельный сценарий «Что приготовить?».

- Хранить отдельную базу продуктов и готовых блюд, которые были попробованы вне домашней кухни.

- Дать двум владельцам удобный CRUD-интерфейс; посетителям - безопасный режим просмотра.

- Обеспечить надёжное хранение данных, изображений и возможность резервного копирования.

## Вне текущего scope

- Интернет-магазин, корзина, оплата и доставка.

- Социальная сеть, комментарии посетителей, подписки и публичные профили.

- Избранное, чек-листы ингредиентов/шагов, встроенные таймеры.

- Публичная регистрация пользователей.

- Мультиязычность на первом этапе.

# 2. Пользователи и права доступа

| **Роль**                | **Права**                                                                                                                 |
|-------------------------|---------------------------------------------------------------------------------------------------------------------------|
| Посетитель              | Просмотр опубликованных рецептов, каталога, раздела «Что приготовить?» и раздела «Пробовали». Без права изменения данных. |
| Владелец 1 / Владелец 2 | Равные права на создание, редактирование и удаление рецептов, заметок, изображений, категорий и записей «Пробовали».      |
| Система                 | Скрывает служебные действия от посетителей и проверяет права на сервере, а не только в интерфейсе.                        |

Публичной регистрации нет. Предусматриваются два аккаунта с обычной аутентификацией по логину и паролю. Оба владельца имеют одинаковые права. Удаление значимых сущностей требует подтверждения.

Черновики должны быть отделены от опубликованных материалов. Точный UX их просмотра владельцами может быть уточнён, но публичный посетитель не должен получать доступ к неопубликованному контенту.

| Даты            | Системное          | Создание, обновление, публикация.                                                   |

## 4.2. Ингредиенты

- Ингредиенты хранятся структурированно, а не одной строкой.

- Каждый ингредиент связан с продуктом, количеством, единицей измерения, примечанием и порядком.

- Поддерживаются группы ингредиентов: например «Основное», «Для соуса», «Для крема». Группа может отсутствовать.

- Количество может отсутствовать для формулировок вроде «соль - по вкусу».

- Единицы измерения являются отдельным справочником.

- Количество порций можно вводить вручную; позднее количество ингредиентов пересчитывается пропорционально.

## 4.3. Шаги приготовления

- Шаги имеют фиксированный порядок.

- Каждый шаг содержит заголовок и текст.

- Фото шага опционально и в интерфейсе выводится после текста шага.

- Отдельное время для каждого шага не используется.

## 4.4. Заметки

- Заметки - важная часть рецепта и располагаются после ингредиентов, до шагов.

- Каждая заметка хранит автора, текст, дату создания и дату изменения.

- Оба владельца имеют равные права на добавление, редактирование и удаление заметок.

- Изменения сохраняются в БД и переживают перезагрузку страницы.

# 5. Каталог, поиск и фильтры

Каталог должен быть пригоден как для быстрого просмотра, так и для точного поиска. Фильтры необязательны: пользователь может не выбирать ни одного.

## Фильтры

| **Фильтр**           | **Тип**      | **Логика**                                                                                                  |
|----------------------|--------------|-------------------------------------------------------------------------------------------------------------|
| Категории            | Checkbox     | Можно выбрать несколько категорий.                                                                          |
| Продукты/ингредиенты | Поле + chips | При нескольких выбранных продуктах используется логика AND: рецепт должен содержать все выбранные продукты. |
| Время                | Radio        | Один диапазон или отсутствие фильтра.                                                                       |
| Сложность            | Radio        | Одно значение или отсутствие фильтра.                                                                       |
| Оценка               | Фильтр       | По текущей оценке рецепта.                                                                                  |
| Сортировка           | Select       | По алфавиту, оценке и времени.                                                                              |

- На desktop фильтры находятся в боковой панели и могут быть sticky.

- На ширине до ~860 px фильтры сворачиваются в верхнюю панель.

- Кнопка открытия показывает число активных фильтров, например «Фильтры · 2».

- Кнопка «Сбросить» имеет смысл только при активных фильтрах.

- Карточки рецептов содержат минимум фото, название и время.

# 6. Страница рецепта

Страница рецепта считается основным эталоном визуального и функционального уровня проекта.

## 6.1. Верхняя часть

- На desktop: двухколоночная композиция - информация слева, крупное основное фото справа.

- Верхняя служебная строка содержит ссылку «К рецептам».

- Название, описание и category chips расположены в левом блоке.

- Метаданные: подготовка, готовка, сложность, рейтинг и статус рецепта. Статус отображается в той же визуальной системе, а не отдельным badge.

- На tablet после перехода фото вниз содержимое intro перераспределяется так, чтобы не оставлять большую пустую область справа.

- На mobile интерфейс становится одной колонкой без горизонтального overflow.

## 6.2. Ингредиенты и порции

- Ингредиенты располагаются в отдельном блоке.

- Контрол порций: «- число +». Нативные browser spinner arrows скрыты.

- Количество порций позже должно менять количества ингредиентов; ручной ввод числа сохраняется как требование.

## 6.3. Заметки и действия

- В блоке заметок есть список заметок и форма «Добавить заметку».

- У каждой заметки доступны «Редактировать» и «Удалить» для владельцев.

- Лишний eyebrow «Из тетрадки» не используется.

- Визуально у заметки допускается одна акцентная вертикальная линия; divider не должен пересекаться с ней.

- Действия «Редактировать рецепт» и «Удалить рецепт» располагаются внизу страницы после всего контента, перед footer.

## 6.4. Шаги и источник

- Секция «Как приготовить» содержит последовательные шаги.

- Если у шага есть фото, оно выводится после текста.

- После шагов выводится источник, если он задан.

- Не используются советы, таймеры, декоративные food-icons, «избранное», печать и время отдельных шагов.

# 7. Раздел «Что приготовить?»

Отдельная страница должна помогать случайно выбрать рецепт. Рандом не объединяется с обычным поиском в один элемент интерфейса.

- Базовый сценарий: получить случайный опубликованный рецепт.

- Допускаются необязательные фильтры, ограничивающие выбор.

- Результат должен вести на обычную detail-страницу рецепта.

- При повторном запуске пользователь может получить другой подходящий рецепт.

- Пустой результат должен иметь понятное состояние без ошибки страницы.

# 8. Раздел «Пробовали»

Отдельный CRUD-раздел для продуктов и готовых блюд, которые пользователь и Кирилл пробовали вне основного каталога рецептов.

| **Поле**              | **Требование**                                        |
|-----------------------|-------------------------------------------------------|
| Название              | Обязательно.                                          |
| Фото                  | Опционально.                                          |
| Категория             | Обязательно или выбирается из справочника.            |
| Производитель / место | Опционально; например бренд, кафе, ресторан, магазин. |
| Оценка                | Одна текущая оценка.                                  |
| Заметка               | Свободный текст.                                      |
| Поиск                 | Нужен.                                                |
| Фильтры               | Не требуются на первом этапе.                         |

# 9. Создание и редактирование контента

## 9.1. Рецепт

- Форма должна позволять создать и изменить все поля рецепта, включая несколько категорий, ингредиентные группы, ингредиенты, шаги, заметки, источник, рейтинг и статус.

- Фото рецепта и фото шагов загружаются отдельно; фото шага опционально.

- Порядок ингредиентов, групп, шагов и изображений должен сохраняться.

- Удаление рецепта требует подтверждения.

- Владелец может сохранить рецепт как черновик, а затем опубликовать.

## 9.2. Справочники

- Категории поддерживают вложенность.

- Продукты являются отдельным справочником и затем используются в фильтрах.

- Единицы измерения являются отдельным справочником.

- На первом этапе не требуется сложная система синонимов продуктов.

# 10. Дизайн-система и адаптивность

Визуальная концепция: спокойный retro/editorial с наивными деталями, но без перегрузки. Дизайн должен оставаться цельным и пригодным для реального контента.

| Red / terracotta | #AE4D40     | Header, footer, основные CTA и акценты.          |
| Red hover        | #8F3E34     | Hover/active для красных элементов.              |

## Типографика

- Fraunces — выразительные заголовки.

- DM Sans — основной текст и UI.

- Количество типографических ролей ограничивается; избегать уникального стиля для каждого элемента.

- UI labels в основном uppercase, умеренный letter-spacing; не делать их чрезмерно мелкими.

## Общие правила интерфейса

- Full-width секции + центрированный внутренний контейнер, ориентир max-width 1200 px.

- Избегать тонких декоративных рамок у карточек, если они не несут функции.

- Не использовать хаотичные одноразовые CSS overrides; исправлять источник стиля и переиспользовать семантические классы.

- Не применять !important как обычный способ исправления макета.

- Header на desktop содержит логотип и навигацию; на mobile используется burger-menu вместо переполненной навигации.

- Ключевые контрольные ширины для визуальной проверки: 1280, 1024, 860/828, 768, 640, 480, 375 px.

# 11. Техническая архитектура

## 11.1. Backend и frontend

- Backend: Django.

- На текущем этапе frontend — Django templates + существующий CSS + JavaScript; SPA не требуется.

- Основной код хранится в Git-репозитории.

- Переход на PostgreSQL является целевым для production. SQLite допустим только как локальная dev-БД на ранних этапах.

## 11.2. Основные модели данных

| **Модель**       | **Назначение**                      |
|------------------|-------------------------------------|
| Recipe           | Рецепт и его метаданные.            |
| Category         | Категории с вложенностью.           |
| Product          | Справочник продуктов.               |
| Unit             | Единицы измерения.                  |
| IngredientGroup  | Группы ингредиентов внутри рецепта. |
| RecipeIngredient | Структурированные ингредиенты.      |
| RecipeStep       | Шаги приготовления.                 |
| RecipeImage      | Изображения рецепта, включая cover. |
| RecipeNote       | Заметки владельцев.                 |

## 11.3. URL и серверная логика

- Рецепты имеют slug-based URL, например `/recipes/orzo-s-lososem/`.

- Мутации данных выполняются через POST и защищаются CSRF.

- Проверка прав выполняется на backend.

- Связанные объекты проверяются в контексте родительского recipe, чтобы нельзя было изменить объект через подмену ID.

- После POST используется redirect (паттерн POST/Redirect/GET), если нет причины применять более сложный API.

# 12. Хранение данных, медиа и резервное копирование

- Production-БД должна быть отдельным постоянным PostgreSQL-хранилищем и не зависеть от локального filesystem приложения.

- Пользовательские изображения не должны храниться как static-файлы приложения в production. Нужен постоянный media storage.

- Репозиторий содержит код и миграции, но не `.env`, production secrets, локальную БД и загруженные media.

- Резервное копирование БД обязательно. Должен существовать понятный способ восстановить данные после ошибки или redeploy.

- Редеплой приложения не должен уничтожать пользовательские данные или изображения.

- Перед production deployment должен быть определён провайдер БД, media storage и схема backup/restore; конкретный провайдер не является частью фиксированного ТЗ.

# 14. Критерии приёмки

Проект можно считать достигшим согласованного конечного результата, когда выполняются все пункты ниже.

- Публичный посетитель может открыть главную, каталог, опубликованный рецепт, «Что приготовить?» и «Пробовали» без доступа к редактированию.

- Два владельца могут войти в систему и имеют равные CRUD-права.

- Рецепт создаётся через интерфейс, сохраняется в БД и корректно отображается после перезагрузки.
